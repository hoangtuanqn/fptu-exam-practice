# Bulk FuOverflow source list and "load new data" runs

- Context: the owner keeps a list of FuOverflow exam threads and wants to import the missing ones and refresh the existing ones in one action, without breaking existing users' data. The existing refresh path (`crawl_jobs.refresh`) re-solves answers with AI, deletes explanations and drops extra questions, so it cannot run over the whole catalogue.
- Decision: new tables `fuo_source_urls` (one row per thread id, status per URL) and `fuo_source_runs` (one row per run, `active_lock` unique so only one run is RUNNING). Admin pastes URLs (size limits per paste are the named constants in `backend/src/constants/fuo-source.ts`, kept below the JSON body limit so the validator reports them; links are validated with the same `isFuoThreadUrl`/`parseThreadId` as the import box) and starts a run; `jobs/fuo-source.worker` processes the URLs in the background, one at a time by default (`FUO_SOURCE_CONCURRENCY`), with a pause between URLs and the crawler's own throttling. Before taking each URL the run waits while any user crawl job is QUEUED or RUNNING, so user imports always get FuOverflow first.
- Missing exam: imported through `examImportService.run` (same code as user imports). AI cost: when AI is enabled, a batch of N new threads queues N AI solves (one per exam, as every import does), limited only by the solver's `MAX_CONCURRENT`; there is no extra per-run cap.
- Existing exam: `examMergeService.merge` only appends (new questions at the end with an empty answer, new attachments, fresher comments in comments.txt); it never deletes, renumbers or re-solves. It does nothing when stored question images or names no longer match the thread (`ORDER_CHANGED`). New questions get names/files that avoid every stored name and every file already on disk, and images are written without overwrite. Once new questions are committed, a later failure (attachments, comments) is only logged and the URL still reports the added questions. Comment pages are only re-fetched when questions were added or the last fetch by a run is older than `FUO_SOURCE_COMMENT_REFRESH_DAYS`; otherwise only the thread page is read.
- Concurrency: every import or merge of a thread takes an in-process per-thread lock (`withThreadLock`), so a user's crawl job and the admin run never delete or overwrite each other's half-imported exam. A user job that has to wait for the lock shows the stage "Đang chờ cập nhật đề" while it waits. Valid because the app runs as a single process.
- Failure handling: a FuOverflow login failure (after one automatic re-login) stops the run as `NEEDS_AUTH` and leaves the URL queued; the next start resumes the same run. RUNNING URLs are re-queued when the worker starts (server restart).
- Consequences: a run over N existing exams costs about one thread page per exam, plus one comment page per question for exams that grew or whose comments are older than the refresh window. Progress is pushed to admins on the `admin:fuo-sources` socket event; the end-of-run notice states how many questions were added without answers.
