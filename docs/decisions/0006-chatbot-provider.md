# Support chatbot provider (hybrid)

- Context: the support chatbot (Cóc Pass) can run on a third-party OpenAI-compatible endpoint that has far more token budget than the Anthropic account.
- Decision: an admin setting `chat.chatProvider` picks where Cóc Pass answers: `anthropic` (default, unchanged) or `openai` (OpenAI Responses API, `POST {chatBaseUrl}/responses`, streaming, `store: false`). Only the support chatbot switches. Exam solving, explanations, materials and topic labeling stay on Claude; embeddings keep the existing OpenAI embedding key and code path.
- The OpenAI path reuses everything else: readiness check, history trimming, knowledge/syllabus retrieval, chat log, the same system prompt plus per-turn block, the same tools (converted to function tools), tool loop cap, one-time continue on `max_output_tokens`, usage recording, refund and generic Vietnamese error on failure. Canned greetings and the semantic answer cache are provider-independent.
- Data sent: user questions, recent history and tool output (for members this includes their own balance, history and other `get_my_data` results) go to whichever endpoint the admin configures. Only trusted endpoints should be used.
- Secrets: `chatApiKey` is the only secret field. It lives in the settings table, is never returned to the client (admin sees `hasChatKey` and a last-4 preview), empty input keeps the old key, `clearChatKey` removes it. The key must be printable ASCII without whitespace. The base URL must be https without credentials, query or fragment. One optional extra header (`Name: value`, printable ASCII, reserved and hop-by-hop names rejected) is sent on every call; it is stored and shown to admins in plain text, so it must not carry credentials (put the key in the API key field). Logs carry only status codes and error classes, never the key, headers, bodies or questions.
- The base URL, model and extra header have fixed defaults in `constants/chat.ts` (CHAT_DEFAULTS) so the admin screen only asks for the API key; the API settings can still override them. Switching to `openai` is rejected (400) while the key would be empty after merging with the stored config; switching back to `anthropic` is always allowed.
- Calls are bounded: idle/first-byte and per-call timeouts, a stream size cap, no redirects, and client disconnect aborts the call.
- Limits depend on the provider: per-provider limits in `constants/chat.ts` (`CHAT_LIMITS`) cover the daily batch before captcha, question length, history turns, old reply length, output tokens and tool turns. `anthropic` keeps the original values so Claude cost does not change; `openai` gets higher values because the third-party budget is large. The zod schema allows the highest ceiling and `chat.service` enforces the active provider's limits before the quota check or any model call (400 "Câu hỏi tối đa N ký tự"). `GET /api/chat/config` returns the active `maxInputChars` and `maxTurns` so the UI can match. The captcha after each batch and the route rate limiter remain the abuse gates.
- No schema change: config uses the existing `settings` table with the `chat.` prefix. The admin chatbot screen exposes the new fields in the same change; deploy the backend before the frontend.
