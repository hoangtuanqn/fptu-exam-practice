# 0003 Slide analysis (Pro, token-limited)

**Context.** Pro students want a per-chapter study summary of their own lecture slides, next to the existing "how often this chapter appears in exams" numbers (`chapter_stats`). Slides are private files and the AI calls cost money, so usage must be bounded per user and the files must not be kept.

**Decision.**
- Scope: `POST/GET/DELETE /api/v1/materials` and `GET /materials/quota`. Pro only on the server (`planService.isPro`; ADMIN allowed for testing). Uses the existing admin AI config (switch + Anthropic key); disabled or no key gives a clean Vietnamese error.
- Pipeline (`services/material-job.service`, worker `jobs/material.worker`): one in-process job at a time. pdf.js (`pdfjs-dist` legacy build, loaded lazily in `services/materials/pdf-extractor`) extracts text per page (capped) and raster image areas (operator list walked with the transform stack, clipped to the page); pages with a large raster image or almost no text are rendered one at a time at 100 dpi with `@napi-rs/canvas` and described by Haiku (2 at a time), with Sonnet as fallback when Haiku is unsure (low, or medium with unreadable labels) or its output is invalid. Pages are then assigned to the subject's syllabus chapters in batches, and each chapter is summarised from its own pages only, with page citations filtered to that chapter. Slide text is always passed as escaped JSON inside a data tag; the system prompts say it is data, never instructions. Calls use structured JSON output without thinking through a small client (`services/ai/material-claude.client`) behind an interface, so tests use a fake.
- Exam frequency is joined at read time from `chapter_stats` by the chapter's topic label (`buildTopicItems`), never stored and never produced by the model.
- Token ledger: `ai_token_usage` (migration 0062) records input + output + cache-creation tokens after every call, per user and `feature`. The limit is a rolling window (`MATERIAL_TOKENS_PER_WINDOW` per `MATERIAL_WINDOW_HOURS`, pure math in `utils/token-window`). Checked at upload (text-only estimate), again after extraction (full estimate, before any spend) and before every call. Running out mid-run marks the upload FAILED with when to retry; spent usage stays recorded. The API only exposes percent used and `resetsAt`; a 429 at upload carries the retry time in the message only. The daily cleanup deletes ledger rows older than `AI_TOKEN_USAGE_KEEP_MS` (window plus a margin; raise it if a feature with a longer window starts using the ledger).
- Retention: the PDF lives in a private temp dir (`private/materials` under the server working dir by default, override with `MATERIAL_TEMP_DIR`; the server refuses to start if it is inside the public `STORAGE_DIR`; folder 0700, files 0600), and is deleted when it is no longer needed and always when the job ends. Uploads (pages, figures, summaries) expire after `MATERIAL_RETENTION_DAYS`; the daily cleanup cron deletes them and orphan temp files. Dedupe only within the same user (same sha256 + subject, not FAILED). No sharing.
- Limits are named constants in `constants/materials.ts`: PDF only (magic bytes), `MATERIAL_MAX_FILE_BYTES`, `MATERIAL_MAX_PAGES`, `MATERIAL_UPLOADS_PER_HOUR` per user (successful uploads only), `MATERIAL_MAX_ACTIVE_PER_USER`.
- Upload path: Pro/ADMIN and the AI switch are checked before multer reads the body (and again in the service). The reverse proxy needs a larger body limit for `/api/v1/materials` only (`deploy/nginx-api.conf`).
- Restart safety: RUNNING jobs go back to QUEUED on boot; stored pages, described figures, assigned pages and written chapters are skipped.

**Consequences / known limitations.**
- PDF libraries: `pdfjs-dist` (Apache-2.0) and `@napi-rs/canvas` (MIT, prebuilt native Skia binary per platform: linux x64/arm64 for glibc and musl, Windows, macOS). No AGPL dependency (MuPDF was tried first and dropped for its AGPL licence). pdf.js 6 needs Node >= 22.13. If the canvas binary cannot load on the server, the API still starts (both libraries load lazily); a job that needs to render a page fails with a clear Vietnamese message and the reason is logged.
- Diagrams drawn only with vector paths (no raster image) on a page that has enough text are treated as text pages and not sent to the vision model.
- pdf.js runs on the main thread (its Node build uses an in-process fake worker). The job yields to the event loop between pages and between renders; the upload request still opens the PDF once to count pages (xref only, no page parsing). Follow-up: move extraction and rendering to a `worker_thread` if API latency suffers during jobs.
- Token estimates are rough; the per-call check is what actually bounds usage (two parallel figure calls can overshoot by one call).
- A FAILED upload is not resumed; uploading again starts over (dedupe ignores FAILED ones).
- Deferred: OCR of question text, "what the exams ask that the slides do not cover", PPTX/DOCX input, sharing analyses between users, wiring the token ledger into other AI features.
