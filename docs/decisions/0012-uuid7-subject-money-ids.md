# UUID v7 ids for subjects and money rows

- Context: after decisions 0009-0011 the last auto-increment ids visible to clients were the subject id (`/subjects/<id>/chapter-stats`, `/subjects/<id>/hot-questions`, the `id` of `GET /subjects/<code>`) and the ids of the money rows members and admins see in lists (deposits, wallet history, gift code redemptions, expiring credit lots, Pro purchases). They leak volumes (number of deposits, ledger size) and are guessable.
- Decision: `subjects.id`, `deposit_orders.id`, `wallet_transactions.id`, `plan_purchases.id`, `credit_lots.id` and `gift_code_redemptions.id` are `CHAR(36)` UUID v7 (`@default(uuid(7))`). Columns that point at them follow: `subject_id` of `subject_chapters`, `question_groups`, `question_group_members`, `chapter_stats`, `question_group_stats`, `similarity_job_runs` (its PK) and `material_uploads` (no FK); `bank_transactions.deposit_order_id` (FK) and `referral_rewards.deposit_order_id` (no FK, unique: one commission per deposit).
- Kept INT: the own ids of subject chapters, question groups (and `group_id` columns), group members, chapter stats, bank transactions and referral rewards. None of them identifies a detail page: chapters are addressed by number, groups are rebuilt as a whole every night and only appear as list items, the others are internal ledgers. Subject issues, inferred topics and syllabus chunks key subjects by code. Subject routes by code (`/subjects/<code>`, `/admin/subjects/<code>`, `/mon/<code>`) are unchanged.
- Migration `0081_uuid7_subject_money` follows 0079/0080 (guard, mapping tables, one `MODIFY` per table, `UPDATE ... JOIN`, FKs re-added with the same names). Ids are built from `created_at` plus the old id bits, so `ORDER BY id` still means creation order (wallet history, credit lot tie-break). The guard also refuses orphan `material_uploads.subject_id` and `referral_rewards.deposit_order_id` values instead of nulling them, so no ledger link is lost. Production data is kept; the header lists money checksums (joined to owner email and deposit code) to compare before and after. Measured on MySQL 8.0.30 (laptop SSD): 300 subjects, 30k deposits, 22k bank rows, 200k wallet rows, 20k redemptions, 10k lots, 5k purchases, 4k group members = about 1 minute.
- SePay matching is unaffected: it finds the order by the random deposit `code` in the transfer content, then links the bank row to the order id. Wallet notes and mails name the code, never an id. No signed link or token carries one of these ids, so no legacy lookup is kept.
- API: subject ids in route params are validated with `uuidSchema`; old numeric ids get 422. Response `id`/`subjectId`/`depositOrderId` fields of these records are strings. Breaking change shipped in one step by owner decision: backend (API stopped during migrate) first, frontend right after.
- Consequences: new rows get their UUID from Prisma; two ledger rows written in the same millisecond (deposit + bonus) may list in either order when sorted by id alone, while the balance and each row's `balance_after` stay exact (the display order of same-millisecond rows is not guaranteed). The nightly similarity job keeps its runs (converted in place), so nothing is recomputed.
