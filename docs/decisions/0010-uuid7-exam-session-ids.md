# UUID v7 ids for exams and practice sessions

- Context: exam and practice-session ids were auto-increment ints visible in URLs and API calls (`/exam/...&session=473`), leaking volumes and making ids guessable. Decision 0009 kept them int; this extends it.
- Decision: `exams.id` and `practice_sessions.id` are `CHAR(36)` UUID v7 (`@default(uuid(7))`). Every `exam_id` column that references an exam follows (13 tables with an FK), plus the soft references `free_explain_turns.used_exam_id` and `question_group_stats.last_seen_exam_id`. Child tables keep their own int ids; `exam_questions.id` stays int because embeddings, question groups and FSRS cards/logs reference it.
- Migration `0079_uuid7_exam_session` converts each column in place (`MODIFY ... CHAR(36)`, one table copy per table, index and FK names unchanged) and rewrites values through a temporary old-id -> UUID mapping table; ids are built from `created_at` plus the old id bits as in 0078, so `ORDER BY id` still means creation order. `admin_notices.link` `/admin/exams/<id>` values are rewritten. Guards stop the migration before any change if an orphan row exists.
- Files on disk are not affected: exam images and attachments live under `exams/<thread_id>/` and their paths are stored in the rows, never derived from the exam id. No legacy id column is kept.
- API: route params, query params, body fields and socket payloads that carry an exam or session id are now UUID strings, validated with `uuidSchema` / `uuidParam`; old numeric ids get 422. Breaking change shipped in one step by owner decision: backend (with migration, API stopped during migrate) first, frontend right after.
- Consequences: the nightly similarity job compares a sum of hashed ids instead of an id sum, so every subject is re-run once after deploy. Realtime `exam` rooms are keyed by the UUID; `job` rooms stay numeric.
