# UUID v7 ids for records with a detail page

- Context: records that have their own detail page or endpoint (gift codes, admin notices, marketing broadcasts, Coursera courses and orders, Pro tickets, explanation feedback, answer reports, slide uploads, exam attempts) used auto-increment ints, which leak volumes and make ids guessable in URLs.
- Decision: these ten tables use `CHAR(36)` UUID v7 primary keys (`@default(uuid(7))`, generated by Prisma). Child FK columns (`gift_code_redemptions.gift_code_id`, `coursera_orders.course_id`, `material_pages/material_chapters.upload_id`) follow; the children keep their own int ids. `User`, `Exam` and every other table keep int ids.
- Migration `0078_uuid7_detail_tables` rewrites existing rows: each old row gets a v7 id built from its `created_at` plus the old id bits, so text order of ids still follows creation order. `email_campaign_logs.campaign` `broadcast:<id>` values are rewritten to the new ids.
- API: route params and response `id` fields of these records are now strings; validated with the shared `uuidParam` / `uuidSchema` (`rules/requests/admin.request.ts`). Breaking change shipped in one step by owner decision: backend (with migration) first, frontend right after.
- Consequences: `ORDER BY id` keeps meaning "creation order" (ties inside one millisecond are not strictly ordered). Secondary indexes on these tables are slightly larger (36-byte PK suffix). New tables with detail pages should use the same pattern; ids never need to be generated in app code while Prisma creates the rows.
